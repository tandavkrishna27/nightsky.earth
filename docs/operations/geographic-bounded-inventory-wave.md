# Raw producer bounded inventory engineering

## Cause and implementation

The producer previously recursively inventoried output paths and called disk free-space accounting on every PBF entity and source-hash chunk. It also performed a database file metadata lookup for every node. With large node tables, these repeated filesystem operations dominate useful work. This is a code-path diagnosis supported by the previously retained diagnostic, not a new profile of the second failed run.

`ResourceGuard.check` now checks the monotonic deadline on every invocation. It performs a fresh, uncached full filesystem inventory after 256 check calls or 100 milliseconds since the last completed scan, whichever checkpoint arrives first. The operation bound prevents a fast loop from indefinitely postponing checks, and the clock bound prevents slower loops from waiting for 256 entities. Counting starts again only after a successful scan completes, so a scan taking more than 100 milliseconds does not create an immediate scan loop. Deadline is checked again after scanning/free-space accounting.

Any explicit pending output bytes force a fresh inventory before the write; the pending bytes are added to output, combined-disk and free-reserve checks. Full checks also occur at source verification entry/exit, between native passes, before/after checkpoints, at source completion, before/after each output file, on completed resume and after completion-file writing. Actual source/file opens continue to use `safe_path`; checkpoint replacement now rechecks both paths immediately before replacement. Source SHA256/size/vintage and mutation checks remain in place.

SQLite `max_page_count` is configured before schema creation using floor(scratchBytes / actual page_size), with existing page count checked before accepting a resumed database. This gives a main-database logical file size cap and removes the per-node metadata lookup. A ceiling smaller than one page is refused before schema creation. The cap does **not** include the DELETE rollback journal, temp files or other scratch. Full inventories continue to count database/journal files toward the declared scratch ceiling. Journal growth during a transaction may overshoot that ceiling between cooperative checkpoints; the supervisor's sampled accounting is also not a filesystem quota. Actual retained journal peaks and overshoot, if observed, must be reported by the parent acceptance measurement.

The 100ms/256-call values bound checkpoint frequency, not wall-clock detection latency: a blocking filesystem/native operation, a large record or the scan itself can take longer. Between scans, newly added evidence or path mutation can remain undetected. The next scan revalidates ancestry, directory identities and non-following child metadata; missing paths, scan failures and links/reparse points fail closed. An already-open SQLite handle can keep writing its original inode after an ancestor rename until detection. These checks are not atomic filesystem isolation, and no unbounded cached path/resource verdict is introduced.
