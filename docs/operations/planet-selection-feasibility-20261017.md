# Planet selection feasibility — 17 October 2026

The present single-stream, full-boundary route is **not established as feasible for global production**. Its effective ceilings are much smaller than the advertised one-million candidate rows: at most **169,895 minimally serialized candidate rows** under 128 MiB, and at most **41,186 candidates** under 200 million membership checks with the current 4,854 features, even before geometry/setup costs. Public counts indicate substantial pressure on these limits. They cannot establish the exact accepted count of the absent dated planet. A 95,380,942,829-byte receipt would establish source identity, not resolve these architecture limits; do not recommend it as the next step toward completion on the strength of available disk alone.

## Which limits bind

1. **Candidate bytes:** `global_source.py:407,432–435` repeats full provenance, the 109-byte exact planet URL, revision and caveat in each candidate. The canonical UTF-8 JSONL minimum is 790 bytes with a one-character name/source ID, one-digit way ID, shortest category, zero coordinates and one source. Thus `floor(134217728 / 790) = 169895`; 169,896 rows cannot fit even at these hypothetical minimum widths. Actual longer values reduce capacity. The zero hash and hypothetical date in the arithmetic example are serialization placeholders, never actual source evidence. The separate lineage minimum is 196 bytes per source membership, allowing at most 684,784 rows under its own 128 MiB ceiling. Exclusions have another independent 128 MiB ceiling. A 385 MiB raw aggregate output allowance cannot substitute for any individual stream cap.
2. **Membership work:** `boundary-metadata.ts:15,34,36` charges one check for every feature classifier, even on a bounding-box miss, plus candidate iteration and writing. All 4,854 retained features are considered per candidate. At least 4,856 checks per candidate means `floor(200000000 / 4856) = 41186`; 41,187 cannot finish with the current feature set. Geometry parsing, vertex/bounds work, actual containment, region output and completion consume the same budget, so the actual maximum is lower and remains unmeasured. The earlier 23-candidate result is not a scale demonstration.
3. **Node stop:** selected-reference mode still counts **all valid nodes encountered per source**, not only selected references or tagged nodes (`global_source.py:371–390`). The official database metadata lists 10,941,937,381 nodes, of which 297,655,726 are tagged. The proposed ten-billion valid-node stop is below that total. Different snapshots and native validity prevent proving an exact dated-body failure from this count, but the stop is a material feasibility risk before candidate emission. No limit was raised.
4. **Publisher:** its configurable ten-million input rows and 10 GiB byte maxima apply downstream. `maxRows=10000` is a page-size maximum. Internal sort merging and ID dedup cannot bypass upstream assembly's one-million-row, 128 MiB, work or 30-minute caps. Memory, scratch, wall time and final catalogue performance remain unmeasured.

## Smallest next implementation

First remove the avoidable all-feature-per-candidate floor with a **bounded spatial broad phase** over the same immutable boundary features. It must conservatively retain the existing tolerance, ambiguous/unknown membership and exact containment result; bound index construction/memory/work and charge those costs to the existing budgets. A meaningful scale fixture must show that the implementation avoids visiting all 4,854 features for every candidate, while preserving boundary, hole, tangent, dateline and unknown results. This addresses the earliest demonstrated architecture ceiling; it does not establish global stream or node fit.

If the accepted global stream exceeds 128 MiB, the next missing facility is an **admitted candidate-partition build and merge path**. `membership-assembly.ts:15,70–76` and `boundary-metadata.ts:18,36` accept one candidate stream; existing boundary shards only partition boundary storage. No candidate partition descriptor, independently completed partition merger or consumer partition-set root exists. A bounded implementation would need explicit ownership and exact-ID conflict/dedup semantics, complete lineage/exclusions, common revision and admission binding, completion/resume evidence and a final root accepted by `server/places/catalogueFormat.ts`. The publisher's internal sort runs do not supply this contract. This is a precise gap, not an implemented or authorized global build plan. Blindly increasing caps or omitting unnamed/relation evidence would not fix it.
