# NightSky V1 MCP tool contracts

This document freezes the model-facing V1 contract surface before MCP registration. These are schemas and product promises, not claims that the providers or handlers are already implemented. Provider-specific fields, forecast horizons, climatology statistics, and licenses remain gated by the source spikes in `source-spikes.md` and the Task 0 decisions.

## Shared wire rules

- Structured results are capped at 64 KiB after JSON UTF-8 encoding. Preserve required source attribution and caveats; trim optional hourly detail first.
- Results expose at most 8 source records, 20 caveats, 25 sky events, 10 observing-location candidates, 4 independent weather forecasts, 48 weather samples per source, 8 plan windows, and 5 comparison options.
- Every external value is tied to a `SourceRecord`: source name and URL, attribution, data class, plus provider model/product and issue/valid time or vintage when supplied. Calculated values identify the calculation/source and algorithm provenance.
- Weather records represent one provider/model each. They include valid times, forecast lead, units, and per-field omissions. Do not average distinct models into one forecast. Historical reanalysis is labeled historical and never presented as a forecast.
- Every result has an `Availability` (`available`, `partial`, `stale`, `unavailable`, `not-covered`, `unknown`, `unsupported`, or `out-of-horizon`) and a human-readable reason. Source gaps and uncertainty remain visible.
- All instants are UTC ISO-8601 strings ending in `Z`; all user-facing time windows also carry an IANA time zone. The maximum requested range is 366 days.
- `PlaceRef` contains a versioned opaque `placeId`, display name, IANA time zone, source records and gazetteer vintage. Exact coordinates for a named place stay in the server-private `ResolvedPlace`. Public observing candidates can expose their mapped coordinates and navigation link. Approximate host coordinates are request-only and never returned or persisted.
- Locale and unit preferences guide presentation. Source-provided names and scripts are retained; the API does not promise translation that the source does not provide.
- Inputs reject unknown fields. Location-aware tools downstream of `resolve_place` accept only a versioned `placeId`, never free-text coordinates or a street address.

## Frozen tool inventory

All tools are read-only and non-destructive. Annotation tuple order is `readOnlyHint / destructiveHint / openWorldHint`.

| Tool | Input contract | Structured result | Annotation | Contract and availability notes |
|---|---|---|---|---|
| `resolve_place` | Exactly one: non-empty named `placeQuery` with `useApproximateHostLocation` omitted/false, or `useApproximateHostLocation: true` without a query. Host hint is read only on explicit true, when a documented hint is available; resolve it to a named place and discard the hint. Missing hint returns `unavailable`, reason `host-location-unavailable`, and requests a named place. Never reverse-geocode user-entered coordinates or claim exact timezone polygons. |

The source-data gates still control implementation: exact public datasets, field sets, horizons, refresh cadence, and attribution/licensing must be evidenced before live handlers use them. The annotation booleans are explicit even when a handler is not yet registered.

## Core schemas

The TypeScript/Zod v4 source of truth is under `shared/nightsky/`:

| Contract | Module | Required guarantees |
|---|---|---|
| `PlaceRef`, private `ResolvedPlace` | `places.ts` | Versioned public ID and provenance; exact named-place coordinates only in server-private record. |
| `TimeWindow`, `SourceRecord`, `Availability` | `common.ts` | UTC order/range and IANA validation; traceable provider/calculation provenance; explicit availability reason. |
| `WeatherForecast`, `NightConditionsResult` | `weather.ts` | Forecast-only data class, independent source records, forecast lead, per-time values and missing-field reasons. |
| `AstronomyWindowResult`, `TargetVisibilityResult`, climatology | `astronomy.ts` | Local intervals and polar state; target geometry; historical statistic separated from forecast. |
| `EventResult` | `events.ts` | Ordered optional event times, explicit local visibility state, source record per event. |
| `PlanResult`, comparison and app recommendations | `planning.ts` | Sources/caveats/gaps retained, explicit factors and actionable preparation. |

## Permissions and privacy

No OAuth, account access, writes, or user data storage are part of V1. The assistant should set the approximate-location flag only for an explicit “near me/current area” request. The service may send rounded destination coordinates to the selected provider, as described in the product privacy notice. Do not log or persist host location hints or query histories. Apply request budgets and privacy-preserving rate limits when the hosting decision is made.
