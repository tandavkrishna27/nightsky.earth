# Offline historical release publication

This engineering route publishes existing validated aggregate tiles; it does not acquire observations or establish a real baseline or global coverage. Retained 2025 sample labels and 1991–2020 baseline eligibility remain authoritative. Runtime delegates statistics to the existing provider, retaining 90% completeness, 27 represented years and the annual/year 80% guards in the validated aggregate construction.

Call `publishClimateRelease({ inputs: [{ inputPath, expectedSha256 }], outputDirectory, generatedAt })` from `scripts/era5/build-release.ts`. Every input is an existing schema 2 tile envelope, at most 8 MiB and ten tiles. Inputs are processed sequentially. There are at most 1,000 shards / 10,000 explicit cell and IANA timezone pairs; this is a bounded engineering ceiling, not worldwide admission. Method, grid, period, builder/astronomy/timezone versions, provenance, caveats and index vintage must agree across shards. Each shard retains its exact actual source revisions. The root records their deterministic union (at most 10,000 identities); a shared kind/revision identity with different checksums is rejected. Missing pairs stay unknown/not-covered.

The candidate identity hashes exact input absolute paths and checksums plus generation time and builder version. Keep these identical to resume. A candidate checkpoint and exclusive publication lock protect the output. Completed shards are immutable and resume verifies their manifests, every tile checksum/size/schema and their exact content against the pinned original envelope. Incomplete shards stop for operator inspection. Changed input identity requires a new output directory. No checkpoint alone makes a release eligible. The final root manifest is published last; configure only that final file and its returned digest. Published roots reject overwrite.

Serving selects `createReleaseEra5ClimateProvider` explicitly through `NIGHTSKY_ERA5_RELEASE_MANIFEST` and `NIGHTSKY_ERA5_RELEASE_SHA256`, mutually exclusive with legacy artifact configuration. Root size is at most 4 MiB, each shard index at most 4 MiB, and each tile at most 8 MiB. Runtime holds only the root descriptors and a bounded LRU of shard providers (default two, maximum eight), whose tile caches share a 32 MiB maximum budget. A maximum sixteen admitted requests are serialized; excess requests return unavailable. This also coalesces identical requests through the completed tile cache. No catalogue-wide tile load occurs.

Every shard and tile is pinned by checksum and exact size; relative paths reject traversal, absolute paths, aliases and symlinks. Root/shard metadata and explicit coverage must agree. Corrupt or missing configured evidence yields unavailable, never substituted observations. Candidate generation and publication are offline and do not change CDS credentials, account state, model versions or deployment.

Validation: `node --import tsx --test tests/providers/climate/release-publication.test.ts`. Fixtures are synthetic engineering aggregates and supply no climate evidence. These checks cover twelve pairs across four shards, independent pair lookup, sample labels, missing timezone pairs, bounded cache bytes, interruption/resume, immutable replay, deterministic output and malformed/checksum/path/duplicate/method rejection. Existing tiled and legacy tests remain the compatibility checks.


CLI: `node --import tsx scripts/era5/build-release.ts --config <absolute-config.json> --expected-config-sha256 <digest>`. The checksummed JSON config contains `inputs`, `outputDirectory`, `generatedAt`, `maxTotalInputBytes`, `maxOutputBytes`, and `maxDurationMs`; unknown fields are rejected. The configuration is at most 1 MiB. Byte budgets are positive integers at most 1 GiB each and time is at most 1,800,000 ms. Function callers can omit budgets to use these ceilings. Inputs stay sequential and at most 8 MiB each. Output accounting includes tiles, shard manifests/reports, candidate checkpoint and the final root. Gates run throughout reading/validation/publication; they are cooperative checks, not an OS resource quota. A failed budget leaves evidence and no final root. An individual existing shard publisher also retains its ten second deadline. Future resumed invocations have their own overall elapsed budget and re-account every retained shard.

The release tests also exercise actual MCP loopback calls at two covered pairs, eight concurrent identical requests with one tile read, independent legitimate regional source lineage and conflicting identities, changed method/period, completed shard corruption before resume and total input budget failure.

Output admission first reads pinned inputs sequentially without candidate writes. It reserves the exact candidate checkpoint, the projected root size (using the maximum shard-size digit width), each input-envelope byte length plus 4 KiB for publication path/manifest overhead and 64 KiB per shard report. These conservative allowances may reject a tight budget even when a measured final release could fit; choose a reviewed budget rather than relying on minimal packing. Each existing shard publisher receives at most the remaining release allowance after checkpoint/retained shards/root reservation, capped at its existing 32 MiB publication limit. The pending root is renamed rather than copied, so its bytes are counted once. Tests sum logical files after checkpoint-sized and final-root-sized budget rejections to check that retained output stays within the requested bound. This remains an application admission limit, not a filesystem quota.
