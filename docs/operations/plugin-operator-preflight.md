# Offline operator preflight

`config/plugin-operator.example.json` is a separate redacted template. It passes the strict structure schema and deliberately returns `incomplete-owner-inputs`. Unknown fields at every object level, including environment and credential fields, fail closed. Keep evidence as opaque record references; never put credentials or private identity details in this file.

Run with an explicit configuration file:

```text
node --import tsx scripts/plugin-operator-preflight.ts --config config/plugin-operator.example.json
```

Exit codes: 0 means `offline-pass`; 2 means `incomplete-owner-inputs`; 1 means invalid configuration, missing/corrupt artifact, or unsafe input. Output contains fixed finding codes only, with `hostChecksPerformed:false`, `deploymentReady:false`, and `officialAccepted:false`. Exceptions, local paths, environment values and input contents are never printed. The CLI imports safely and never reads process environment. Configuration input is bounded to 1 MiB. No network requests, DNS lookups, account access or runtime changes occur.

## Required explicit choices

Set `status` to `selected` only after entering actual decisions. Supply distinct production and staging HTTPS `/mcp` endpoints, HTTPS policy/support URLs, and an exact bare DNS host allowlist covering both service hosts. Credentials, queries, fragments, wildcards, local/example hosts and IP URLs are rejected. Choose `NODE_ENV=production`, listener HOST/PORT and mode explicitly. Runtime listener, tool mode, regional/global exclusivity and proxy validators are the actual exported server contracts. Host reachability remains untested.

Direct topology disallows trusted proxy peers. A single rewriting proxy requires narrow runtime-valid IP/CIDR peers plus header replacement and restricted backend evidence. These evidence references express an operator decision; preflight cannot prove firewall rules, TLS, DNS, forwarded-header behavior or public-route isolation.

Full mode additionally requires the confirmed MET contact in its User-Agent, GeoNames inventory and path, one pinned OSM/global selection and one pinned historical selection. Resolver-only can omit these product artifacts, but any selection explicitly present must be paired, pinned and verified. Historical release uses `NIGHTSKY_ERA5_RELEASE_MANIFEST` plus `NIGHTSKY_ERA5_RELEASE_SHA256`, mutually exclusive with `NIGHTSKY_CLIMATE_ARTIFACT` plus `NIGHTSKY_CLIMATE_SHA256`. The global and regional runtime parsers enforce their mutual exclusions. GeoNames uses independently pinned inventory rather than an invented SHA environment variable.

## Immutable inventory and resource admission

Every artifact has an opaque ID, kind, relative path, SHA256, exact byte length and version. Every release lists its explicit artifact IDs (at most 10,000). Legacy schema-3 history and catalogue formats require all referenced components explicitly as `component` entries. An explicitly pinned schema-4 climate catalogue additionally authorizes its contained child release, shard and tile dependencies through exact descriptor hashes and byte lengths; these files may be omitted from the flat list. This authority applies separately to current and rollback and cannot authorize unrelated files. Paths are relative to the configuration directory and must stay inside it. Absolute paths, traversal, backslashes, alternate stream syntax, symlinks in artifact path components and nonregular files are rejected. Files are read in fixed 64 KiB chunks with an explicit per-artifact ceiling (maximum 16 GiB), checked length/hash, and before/after file metadata checks. No unbounded world dataset read or loader cache population is performed.

Supported catalogue and history formats receive dependency closure and existing loader validation. Source completeness, geographical coverage truth, scientific acceptance and actual host capacity still require the owning data lane and operator evidence. Retain the provenance and coverage records for runtime acceptance. Ordinary read-only checks cannot guarantee immutability against a privileged concurrent adversary; preserve read-only immutable mounts and rerun verification at promotion.

Budget requires process count, memory ceiling, disk available evidence, current and rollback allocations, scratch, reserve, per-artifact ceiling and capacity/rollback evidence references. Preflight checks the sum of **current + rollback + scratch + reserve**, using integer arithmetic, against supplied available bytes, and verifies each release's explicit and derived bytes fit its allocation. Matching explicit dependencies count once within that release. Each dependency absent from the flat list is charged per descriptor occurrence, so reused references can conservatively overcount; the result does not claim unique physical bytes. Shared files count in both current and rollback allocations conservatively. Closure reads one child, shard and tile at a time, limits verified reads to 3,000,000 and elapsed time to 30 minutes, and stops before derived bytes exceed the release allocation. Existing per-file limits still apply (4 MiB child/shard and 8 MiB tile). These are offline admission bounds; full global coverage and an actual feasible host remain unproven. Supplied free space is evidence input, not a reservation or fresh actual-host measurement. Process/memory values are declared limits, not a benchmark or provider entitlement. Never reuse the old 1 TiB plus reserve proposal without a measured feasible envelope.

## Promotion and rollback selection

`selectRelease(config, 'current' | 'rollback')` returns a detached copy of a structurally valid immutable source commit, built image digest, architecture, package version and artifact-ID tuple. It performs no mounting, file replacement, pointer update, image pull or process restart. Run `operatorPreflight` and inspect the selected release inventory before using this plan. Current and rollback IDs/images must differ and architecture must match. Preserve complete source/image/artifact/version tuples and all previous artifact files; changing only a manifest path is not rollback.

Owner evidence must cover identity, policy approval, retention, exact host decisions and provider budgets as redacted references. Even an offline pass closes none of the actual-host streaming/capacity/TLS/firewall checks, intended-client journeys, official review, publication or deployment authorization gates described in `v1-host-policy-handoff.md` and `local-package-readiness.md`.

Inventory admission rejects every artifact not assigned to current or rollback (ARTIFACT_UNASSIGNED), ensuring every verified retained file is charged to at least one release allocation. Release selection rejects schema errors with a fixed message and does not expose unknown property names.

## Exhaustive release closure (offline)

Preflight follows every published global catalogue root and page reference, including directory, ID and membership references. It follows every history schema 3 root to schema 2 shards and every tile. Existing schemas and history semantic validators check revisions, sample/method metadata, shard coverage keys and tile statistics. For global catalogues and standalone history schema 3 roots, each referenced child must have the exact relative path, SHA-256 and byte count in the **same release** inventory. For an explicitly pinned history schema 4 root, trusted ancestor descriptors authorize contained children with exact SHA-256 and byte count; those derived dependencies are charged to that release allocation even when absent from its flat inventory. Paths are contained and links refused. Distinct artifact IDs cannot alias the same case-insensitive path. A shared immutable file can be retained by listing its one artifact ID in both release allocations.

`RELEASE_CLOSURE_INVALID` reports malformed roots, incomplete or mismatched references and invalid shard/tile identity without disclosing local paths. Missing and mutated inventory files fail the existing streaming artifact verification. Candidate checkpoints and publication receipts are not substitute roots. A publisher interrupted before its final root remains inadmissible; resume must verify and finish the immutable publication first. Extra support files must still be explicitly assigned, pinned and budgeted.

The focused operator tests build a real paged catalogue and publish a fictional history release through interruption and resume, then rehearse unlisted and cross-release allocation, corruption and missing children. These are offline fixture and recovery measurements. Inventory byte totals are checked against the declared current/rollback allocations; they do not measure production RSS, disk headroom or host capacity. Capacity and rollback evidence remain owner inputs. Selection returns a copied release tuple only and performs no runtime change. `hostChecksPerformed`, `deploymentReady` and `officialAccepted` remain false after every outcome.


Offline fixture measurement from the 2026-10-15 focused operator run: the resumed fictional history release inventory contained **7 files / 79,313 bytes**, including its checkpoint and publication receipt; exhaustive preflight took **15.50 ms** on that run. The nested wrong-tree rejection fixture contained **8 files / 1,615 bytes**, and rejection took **10.28 ms**. Tests emit the current measurements on every run; elapsed time varies with the machine and load. These figures measure fixture files and local execution only, and provide no host RSS or production capacity acceptance.
