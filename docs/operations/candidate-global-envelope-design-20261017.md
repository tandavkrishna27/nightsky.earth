## Decision

Add an explicit version-3 assembly/capacity contract separating cumulative validation operations/lexical tokens from geometry comparisons. Keep one shared absolute deadline, cumulative physical read bytes and row accounting across every partition and verification pass. Keep all current hash, order, duplicate-key, provenance, frozen-count, unexpected-part, source/admission/code identity and final revalidation protections.

Version 3 also makes candidate-row and enriched-output budgets explicit invocation controls, coupled to the raw producer and existing publisher limits. This is required to support the intended global candidate envelope, rather than solving only physical file partitioning. It is not approval of a particular global allocation or evidence that the dated planet fits one. No current count or time/output limit is silently raised for v1/v2.

Options considered: increase the single mixed-unit work number (rejected: obscures geometry cost and makes validation byte growth consume the geometry allowance); skip repeat parsing/hash checks (rejected: weakens immutable handoff protection); separate units with explicit cumulative limits (recommended). A future validated lease/witness optimization may reduce passes, but is outside this change.

## Exact current work-floor derivation

`parsePartitionJson` charges one shared work tick for each JSON string or punctuation token. A finite serialization of the retained hypothetical one-source minimum row charges **82 lexical ticks**. Its lineage row charges **21**; an exclusion row with three string fields charges **13**. Number spelling and string length do not reduce these fixed structural tokens. Actual extra sources/regions/fields add tokens.

Every successful current assembly necessarily traverses:

| Body | Passes | Reason |
|---|---:|---|
| Raw candidate family | 4 | Initial complete verification, classification iterator, post-classification verification, final raw verification |
| Enriched candidate family | 4 | Bridge precheck, publisher input, bridge postcheck, captured final verifier after admission/raw checks |
| Raw lineage family | 3 | Each complete raw verification |
| Raw exclusions | 3 | Each complete raw verification |

With A accepted candidates, L>=A lineage rows and E exclusions, lexical work alone is at least `8*82*A + 3*21*L + 3*13*E >= 719*A + 39*E`. This deliberately omits all metadata tokens, row/checkpoint/I/O/ordering/provenance operations, writing, geometry setup, BVH and containment. Therefore current shared 200,000,000 work admits at most **278,164 candidates even if E=0 and every omitted cost were zero**. Conditional on the later metadata's at least 684,908 park exclusions, that upper bound falls to **241,013** before every omitted cost. This is a deterministic implementation bound, not a throughput extrapolation.

The opt-in 16,000-row test observed 28,053,328 total shared ticks, but its four long sources and two simple boundary features are not a workload model. The full 4,854-feature retained diagnostic found exact containment dominated its 500 border-heavy samples; neither that distribution nor its timing predicts selected planet points.

## Proposed v3 controls

Keep raw manifest/completion layout v2: selection and raw byte emission need no new wire. Require assembly schemaVersion 3 and capacity schemaVersion 3 / kind `partitioned-geography-capacity-v2`; reject mixed assembly/capacity versions. The exact compatibility matrix is raw1/assembly1 (legacy, no v3 capacity), raw2/assembly2/capacity2, and raw2/assembly3/capacity3. TypeScript admission and the Python supervisor must implement this same explicit matrix with strict duplicate-key parsing for v2/v3 controls, not remove equality checks or permit raw3. The old equal-version test cannot simply be removed. Capacity raw limits still exactly match the executed v2 manifest. Full plan/capacity bytes and versioned resource fields participate in the fixed admission snapshot. V1/v2 parsing and behavior remain unchanged.

Required fields, with no defaults:

- `membership.maxRows = C`, positive safe integer, `C <= raw.limits.candidates` and `C <= catalogue.maxInputRows <= 10,000,000`. Remove the v2 one-million restriction only in this strict v3 branch. Do not hardcode a transient public-count observation into generic source code. A proposed reviewed stress envelope is **C=2,281,141**, covering every later predicate occurrence as a candidate; it is deliberately more conservative than the conditional 1,472,705 accepted upper bound. It is a test/proposal envelope, never an exact-body guarantee or auto-selected execution value.
- `membership.maxOutputBytes = M`, explicit safe integer. Require `M <= 64*134217728 + 134217728 + 1048576`: bounded enriched parts plus the existing bounded common-region stream and completion descriptor; generated footprints stay empty. `allocations.membership >= M`. Publisher and configured stream input byte allowances must cover the admitted enriched candidate allowance plus region and original footprint inputs, rather than raw candidate bytes alone. Capacity must reserve these aggregate input bytes and retain explicit <=10,000 metadata rows, sort/output controls and existing 10 GiB maxima. Enriched candidate input plus common publication metadata must fit these explicit allocations. Footprint metadata remains separately admitted. Keep emitted row <=65,536 bytes, parts <=128 MiB and at most64. Raising C alone cannot pass if M is inadequate.
- `membership.maxGeometryComparisons <= 200,000,000`, explicit. Geometry parsing/vertices, BVH construction/traversal and exact containment consume this ledger. Keep full known/unresolved inventory, tolerance and all unknown semantics. Do not rename or rebaseline legacy/v2 reported work.
- `validation.maxLexicalTokens`, `validation.maxOperations`, `validation.maxReadBytes`, `validation.maxRowsRead`, all explicit positive safe integers. One cumulative object survives every raw/enriched pass, metadata check and writer; no per-part/per-phase factories. Every duplicate-key/depth scanner token charges the lexical ledger; each existing nongeometry check/iteration/EOF/provenance/metadata/I/O checkpoint charges operations. Body/row reads charge physical bytes/rows. Emitted writes have distinct counters and allocation views: the current writer charges bytes/rows to its supplied budget, so those counters must not merely be renamed reads. Raw/enriched read views and membership write views route to separate session counters while sharing validation operations/deadline. Boundary staging writes, membership parts/common metadata/completion, assembly control/marker writes and publisher writes remain separately attributable to their existing capacity allocations; physical reads never include a write and output bytes never buy a read allowance. Geometry I/O and hashing are validation; per-vertex/topology/index/containment steps are geometry. Checks that do both charge both as appropriate. Abort and the single deadline apply to both.
- Preserve the current raw/enriched/footprint physical-read reservation `Rparts=4*(B+M+F)+8 MiB`, where B is admitted aggregate raw output and F the admitted footprint bytes. Require `maxReadBytes=Rparts+3*G+Q` using safe arithmetic: G is admitted aggregate boundary bytes; three G passes cover staging copy, session geometry load and session revalidation. Required explicit `controlAndAdmissionReadBytes=Q` covers bounded control bootstrap and every physical code/metadata/geometry/footprint read performed by the two Node assembly admission phases, including linked authority validator reads; actual bytes charge this subledger as well as the total. This does not include raw-producer or supervisor-preflight processes, whose separately bounded stage accounting remains unchanged. Q is an allowance, not an inferred observation or disk allocation. Start the absolute timer before bounded control bootstrap (plan<=1MiB, capacity<=64KiB, raw manifest<=1MiB), seed its actual read/operation totals into the session and pass that same session through both assembly gates before any output work. Existing admission distinct metadata/geometry/code limits remain in force. Every subsequent body read must reserve/charge before allocation/read; no gate or linked validator can bypass Q or total bytes. The v3 plan lists the finite Q and resulting maxReadBytes; neither ledger resets on entering membership/publication/final verification. Lexical tokens are at most the bytes actually lexed (each matched token occupies at least one byte), so `maxLexicalTokens <= maxReadBytes` is a structural ceiling, not a sufficient-budget promise. Before opening part bodies, validate completed raw descriptor counts against `82*4*A + 82*4*A + 21*3*L + 13*3*E` as a necessary lower bound for the declared lexical budget; extra source/membership tokens and all other validation costs still require headroom. Pre-producer review uses the proposed candidate/evidence-row envelope, never fabricated actual counts. Insufficient declarations fail early; meeting a lower bound does not guarantee completion.
- `membership.maxMilliseconds <= 1,800,000` and the publisher's <=1,800,000 remain unchanged in this implementation. One session `startedAt/deadline` is established before bounded control bootstrap/assembly admission and before first partition-validation work and preserved throughout. Parsing capacity controls cannot create a new deadline for each subsequent phase. If a real invocation needs longer, that is a separate explicit wall-time review with observed stage rates; this proposal does not grant it.

Use a typed shared resource session with named `validation` and `geometry` ledgers, shared deadline/abort and distinct metadata map. Require the same session in verified-producer handles, the classification session, output writer, publisher bridge and captured final verifier. Carry version-specific row/output/resource limits through boundary session construction, expected accepted counts, strict completion schemas, bridge dispatch and fresh trusted pin verification; no v3 limit may leak into v2. New completion resource evidence is versioned (membership completion schemaVersion 3), with separate lexical/operation/geometry totals, physical read bytes/rows, output bytes and honest elapsed time. Never compare a v3 split total to an old mixed-unit benchmark. Keep consumer root schema 2. The bridge must still check a fresh trusted completion pin before dispatch and reject downgrade/substitution.
