# Bounded ERA5 lineage publication and admission

Schema 6 release roots and schema 5 catalogs implement the bounded lineage contract in `global-history-request-inventory.md`. Schema 2 shards retain at most 10,000 source rows; schema 3 releases and schema 4 catalogs remain supported with their original limits. Source acquisition, serving installation and scientific coverage are separate decisions.

## Explicit publication

The existing release/catalog commands select the new path only when a pinned configuration explicitly supplies `schemaVersion: 6` or `schemaVersion: 5`. Schema 6 consumes existing pinned schema 2 shard manifests, each with at most ten coverage pairs, using `{path, sha256}` inputs relative to the output root's directory. It rereads and validates the actual tile bodies. Schema 5 consumes existing pinned schema 6 roots. Unknown versions fail closed and a failed hierarchical build never falls back to a flat union.

Both configurations contain an absolute `outputPath`, `inputs`, and explicit `budgets`: `maxInputBytes`, `maxMemoryBytes`, `maxScratchBytes`, `maxOutputBytes`, and `maxDurationMs`. The memory minimum is 16 MiB. Maximum configurable memory is 2 GiB; input reads are capped at 64 GiB; scratch and output each have an explicit maximum of 32 GiB; duration is at most 60 minutes. These are offline workstation limits, not changes to tile/manifest sizes or runtime cache allocation. A caller must reserve the combined scratch and output amounts when sharing a disk. Every nested sort and audit charges the same publication budget before writing. The complete synthetic worker divides its remaining combined disk allowance between scratch and output before each publication.

All tree directories are created fresh, output objects are exclusive, and the final release/catalog root is written last. Failure preserves scratch and any unreferenced immutable objects. Recovery requires an operator to select a new output location or explicitly inspect the existing work; there is no automatic retry, cleanup, reuse, or cap increase.

## What is committed

Each source root retains every `{kind, revision, sha256}` row. Source identity is `kind + '|' + revision`; conflicting hashes for that identity fail even across coverage children. Identical rows deduplicate. SHA-256's first four hexadecimal digits route to one of 65,536 leaves. Leaves contain at most 2,000 sorted unique rows and 512 KiB; four levels of nodes have at most 16 children and 16 KiB. The hash commits a domain/version string, prefix, counts, child pins and rows. Strict parsing, fatal UTF-8 decoding, canonical bytes, path checks, prefix validation and subtree counts reject malformed artifacts.

Membership records commit catalog-to-release, release-to-shard and shard-to-source-array identities and digests. Release IDs and catalog IDs derive from their explicitly pinned input inventories, avoiding a cyclic digest dependency. The schema 6 shard descriptor carries its canonical bounded source-array digest and counts. The source root descriptor uses `uniqueRevisionCount`; its nested membership descriptor's `count` counts edges, with per-kind totals representing the rows covered by those edges.

The publisher constructs the release union from the actual source arrays. Before accepting a supplied schema 6 child, the catalog publisher independently sorts its actual shard arrays and compares every deduplicated row against the child tree. It then merges the verified child trees globally. A caller cannot supply a fabricated child tree and matching membership claims to omit a source. Final input revalidation precedes publication of the root.

## Runtime and operator admission

Runtime verifies the pinned source and membership roots, the selected catalog-to-release edge, the selected schema 2 shard, and both shard membership edges. It does not build a flat child/global union or fetch individual source rows for ordinary climatology requests. One shared 2 MiB lineage/membership buffer cache leaves 30 MiB of the default 32 MiB total allocation for tile buffers across the catalog's release/shard caches. Cache keys contain both path and digest. A cold membership lookup traverses at most five bounded objects. Root metadata and bounded parsed descriptors follow the existing manifest admission model; `inspectCache().bytes` reports retained buffer allocations, not whole-process RSS.

Offline operator closure exhaustively visits all pinned tree objects and tiles, and independently verifies the actual shard/source unions and global child union with bounded sorting. This stronger audit needs an explicit optional `lineageValidation: {scratchDirectory, budgets}` on operator configuration (or closure limits). New schemas fail closed without it. The scratch directory must be absolute, fresh, and outside the artifact directory in both directions. The operator creates the explicitly selected base and separate current/rollback directories; nothing is selected automatically. One sort budget is shared across every hierarchical root in each release closure. The operator reserves twice `maxScratchBytes` for retained current and rollback scratch, plus the existing current/rollback artifact allocations; its memory reservation must cover `maxMemoryBytes`. Legacy configurations keep their existing read-only behavior and 30-minute closure bound. Explicit hierarchical validation permits up to 60 minutes.

## Evidence and limitations

Focused tests cover the 10,001-source case, complete small-tree inspection, identical overlap, cross-child conflict, independently repinned omitted rows, malformed UTF-8, missing/altered membership, wrong prefixes, duplicate/reordered keys, excessive leaf rows, count/path tampering, unknown schemas, multi-root scratch accounting, operator configuration and runtime cache bounds. Existing schema 3/schema 4 publication and runtime regressions pass.

The complete 18,033,376 prospective raw/decoded key proof plus 17 synthetic retained/metadata rows uses the frozen schedule and actual 56,039-pair routing. Its separate supervisor pins the executable bundle, Node binary, source files, schedule and pair inventory, and measures the process tree and whole output directory. Its prelaunch estimate is about 18.2 GB logical output/scratch with a 32 GiB disk limit, 2 GiB process-tree memory and a 60-minute deadline. The original provisional 20-minute/16-GiB envelope was revised before execution because complete child/global trees and independent audits require more work. The single supervised run completed successfully; its [sanitized acceptance evidence](data-pilot-evidence/2026-10-16-bounded-lineage-scale.json) preserves the measured source/runtime pins and root digests. All 24 source/input pins and both runtime pins were unchanged after the run.

The full run inspected **18,033,393 unique pins**: 9,016,694 raw, 9,016,696 decoded and three manifest rows. It published all **56,039 coverage pairs** through 5,604 schema-2 shards and six schema-6 children. Every child exceeded 10,000 source rows. The catalog independently compared each child union with its actual shard arrays, then the proof recomputed and inspected every global source pin. All 65,536 global leaves fit the contract; the largest had 346 rows and the largest serialized leaf used 41,411 bytes. A same-key/different-hash conflict across children was rejected.

The supervisor completed in **2,604.625 seconds** (43.41 minutes), with peak sampled main-process RSS **337,317,888 bytes** (321.69 MiB) and peak sampled whole-output logical size **14,554,578,378 bytes** (13.56 GiB). Twelve selected child-boundary queries succeeded, with 163 provider reads and 478,600 retained cache bytes, including 378,650 lineage bytes, across four shards and two children. These measurements fit the declared envelope. Immediate publication write budgets complement the supervisor's 60-second disk sampling; the Windows Job enforces committed-memory/process limits and the supervisor enforces the deadline. The 96 GiB free-space reserve remained part of supervision. Failed-conflict scratch and all other artifacts were retained.

Full operator closure was exercised in focused fixtures, but its complete 18-million-row run was **not separately measured**. The acceptance evidence describes publisher/global-tree validation and selected runtime routing. Four unchanged legacy source files had CRLF checkout bytes and LF Git blobs; the evidence preserves both hashes and records the exact newline-only equivalence. Measured production code and the executable bundle were not rewritten after the proof. Subsequent CI portability fixes canonicalized temporary paths in the two lineage test files; their recorded hashes identify the historical proof inputs, not current test bytes.

All proof source hashes and tile values are explicitly synthetic. Request-derived revision keys are distributed sequentially over the actual sorted pair routes; this does not reconstruct the geographic relationship between acquisition rectangles and real cell observations. The supervisor reports sampled logical file bytes and an independent filesystem free-space reserve, rather than allocated filesystem cluster bytes. No future ERA5 content hashes, scientific completeness, operational request feasibility or deployed coverage follows from this engineering proof.
