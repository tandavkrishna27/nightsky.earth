# NightSky.earth Product Scope V1 to V3

**Status:** Working draft for discussion; product identity confirmed as NightSky.earth
**Last updated:** 10 October 2026

## Purpose

This scope describes a free-to-use, global night-sky planning product in three stages. Every version assumes that users pay nothing and that no paid data/API is a required dependency. V1 is the detailed foundation: it combines public location context, astronomy calculations, sky events, weather and long-range climate context so a person can plan an outing without assembling the answer from several separate tools. V2 and V3 remain proposals.

The product promise is:

> Help me decide where and when to observe or photograph the night sky, what I may be able to see, and what I should prepare for.

“Free” has two separate meanings in this scope: free to the user, and free to access/reuse the data. The product must not depend on a paid API, paid dataset, or a free tier whose terms prohibit the product’s use. Open data still has attribution and license conditions. Free-to-access services may have quotas, no uptime promise, or change without notice. Hosting, map delivery, storage, data processing and maintenance can still cost money, so zero-cost operation at global scale is not promised.

### Public spot data: useful for candidates, insufficient for access guarantees

Public data can materially help discover possible locations. OpenStreetMap includes mapped parks, campgrounds, viewpoints, trails and other points of interest, while government/park sources can provide authoritative details in some regions. Assistant web search can add relevant public pages when available. This is feasible as a V1 candidate-discovery workflow, including a text response without a map.

The limitation is the meaning and freshness of the records, not a total absence of data. Map tags may be missing or stale; a park's existence does not tell us whether it permits night entry, whether a gate is locked, whether a site is seasonally closed, or whether the user can safely reach a viewing area. Coverage and rules vary by jurisdiction. The product should say “candidate location; verify current rules” and cite sources, rather than present the result as cleared access.

Data access also has operational and licensing boundaries. OSM data is available under ODbL with attribution and share-alike duties for qualifying derived databases. The public Nominatim service has strict usage limits and is not an unrestricted production geocoder; public Overpass endpoints likewise should not be treated as a guaranteed production database. Use a deliberate, terms-reviewed retrieval plan (for example, permitted regional extracts, a suitable hosted provider, or official local datasets) and do not scrape websites just because they are publicly viewable. See [OSM copyright and license](https://www.openstreetmap.org/copyright), [Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/), and [OSMF license FAQ](https://osmfoundation.org/wiki/Licence/Licence_and_Legal_FAQ).

## Product direction

NightSky.earth already has editorial material, a meteor calendar and astronomy resources. Plugin V1 adds a cross-platform conversational planning capability around that content. The current website remains as-is for plugin V1 except for any minimal public policy/support pages required by the listing. Website discovery, design, and possible implementation can proceed at the same time as plugin V1 as a separate workstream with its own scope and plan.

A standalone map of dark areas is not enough to distinguish the product. Plugin V1 should help with the decision across the whole outing: where a user might go, which place/date/time best fits a goal, what may be visible, and what evidence supports that answer. Text-based public candidate discovery is in plugin V1; visual map exploration belongs in a separate website scope that can run in parallel.

| Principle | V1 decision |
|---|---|
| Free to the user | The NightSky.earth assistant experience has no subscription, paywall or required account in V1. Keep that assumption for V2 and V3. |
| No paid data dependency | Use data and services with a zero-fee path that permits the product’s intended use. Do not rely on a noncommercial-only free endpoint. |
| Global baseline | Support coordinates worldwide where source coverage allows; show gaps rather than implying equal quality everywhere. |
| Explain the evidence | Show source, forecast time, local time zone, data age and missing fields. Keep cloud, aerosol/haze proxies, ground light emissions, historical climate, and astronomical seeing as distinct things. |
| Treat locations honestly | A mapped park or dark area is a candidate, not a promise that it is legal, open, safe or suitable after dark. |
| Keep V1 read-only | No submissions, reviews, photo uploads, accounts, saved profiles or community features. |
| No plugin database in V1 | Do not add a persistent database for the MCP service. Keep no user accounts, saved plans, or query history; use live provider calls, bounded in-memory cache, local calculations, and compact versioned read-only data files. If a required dataset cannot be served safely as a file on the selected host, mark that capability partial/unsupported and defer it rather than adding a database. This decision applies to the plugin service and does not by itself migrate or remove existing website storage/dependencies. |
| Keep the service replaceable | Put providers behind a small adapter layer so a source can be changed without changing the user-facing tool contract. |
| Keep the web product independent | Keep NightSky planning logic in a platform-neutral service and expose a shared remote MCP interface for compatible assistants. Add platform-specific adapters only where a host requires them; do not assume every marketplace or consumer app supports identical installation or UI. |

## V1 user journey

| Step | User need | Product behavior | Data required |
|---|---|---|---|
| 1. State the goal | “I want to see the Milky Way,” “I have a telescope,” or “I want to watch the Perseids.” | Ask only for the context needed to plan: activity, date range, target and optional equipment/experience level. | Skill instructions and target catalog. |
| 2. Choose an area | “Near me” or a named destination. | Use a user-named place as the portable baseline; use host-provided coarse location only when the assistant supplies it and the user has chosen that flow. Do not assume device GPS access. | Place-name resolution; host location context when available. |
| 3. Find candidates | “Show me places that might work.” | Suggest text-based public candidates using permitted place datasets, official sources and assistant web research where available. Explain why each candidate appeared and cite the source. Do not require a map UI. | Appropriate public POI data and/or host web research, each subject to source terms and coverage. |
| 4. Assess the candidate | “Is it dark, reachable and clear of obstructions?” | Compare available darkness, terrain and public access evidence, but flag missing/stale evidence. A candidate is not proof of legal night access, current opening, safety or clear horizon. Do not label raw satellite light as measured sky brightness or a verified Bortle class. | Public context only where coverage and licensing are established; access must be verified locally by the user. |
| 5. Select a date and target | “When can I see it?” | Calculate astronomical darkness, twilight, Moon conditions and object visibility at the selected place. | Astronomy engine, event tables and target catalog. |
| 6. Check conditions | “Will the sky cooperate?” | Show each available forecast as its own source-labeled set of conditions, including cloud layers, precipitation, wind and temperature/dew point where provided; include aerosol/dust context where available. Keep model forecasts separate from each other, observed satellite imagery and local hazard alerts. | MET Norway is the initial source; add NOAA GEFS when its data path is ready. CAMS and regional official warning feeds are separate context. |
| 7. Plan within or beyond the forecast | “What about next month?” | Show each supported forecast with its source and issue time; any ensemble spread is labeled within that source. Further out, offer historical monthly/seasonal cloud statistics, explicitly labeled as climate history rather than a forecast. | MET Norway initially; optional NOAA GEFS if validated; ERA5 historical reanalysis. |
| 8. Compare options | “Which night or location is the better fit?” | Compare hours, locations and dates for the user’s activity. Explain trade-offs and uncertainty instead of presenting an unexplained universal score. | Planner combining astronomy, weather and location context. |
| 9. Keep the result | “Can I keep this?” | Return a clear, copyable plan in the assistant conversation. Do not create a share page or save location history in V1. Revisit calendar export and share links after the plugin launch based on host support and user feedback. | Structured plan result and assistant response. |
| 10. Prepare | “What should I bring and where do I navigate?” | Produce a checklist based on activity and conditions. Provide an external directions link; V1 does not promise driving time or legal access. | Skill checklist, forecast and destination link. |

## V1 end-to-end journey matrix by user and scenario

The same planning service should support these different users. The assistant asks only for missing details that change the recommendation, then selects the activity-specific factors and tool sequence. Table entries describe the intended end-to-end behavior; availability and confidence still depend on source coverage.

| User and scenario | User starts with | NightSky resolves and checks | Plan returned | Handoff, limits and recovery |
|---|---|---|---|---|

Explain terms plainly. | Link to a sky-identification app such as Stellarium or Sky Tonight if the user wants to point the phone at the sky. Candidate sites are not access/safety guarantees. Do not claim visibility when the event is below the horizon or local circumstances are unsupported. |
| **Traveler planning months ahead** choosing a destination/date | “I’m traveling in October; where is a good chance of clear, dark skies?” | Ask dates, region, activity and flexibility; compare seasonal cloud climatology, Moon/darkness calendar, predictable events and candidate places; keep climatology separate from forecasts. | Explain which dates/areas historically look more promising and why; identify when a real forecast becomes available and invite a later recheck. | Avoid a specific-night weather promise months ahead. Clearly label historical statistics, coverage gaps, access evidence and when conditions should be checked again. |
| **Observer whose forecast changed** deciding whether to go or switch plans | “Clouds moved in—should I change location, time or date?” | Refresh available forecasts and issue times; compare remaining clear windows, alternate dates or other user-approved areas; preserve the original goal and recompute the event/target window. | A concise re-plan that identifies what changed, whether an alternative is materially better, and which uncertainty remains. | Do not imply continuous monitoring or send automatic alerts in V1. User can ask for another check; saved plans and scheduled reminders remain later work. |
| **Observer with mobility or access needs** checking whether a candidate place may work | “Can I get to a dark place with step-free access and nearby parking?” | Search official access/facility information and mapped tags where available; compare user-stated constraints; identify missing, old or conflicting access details. | Return only evidence-backed accessibility details, link to the managing authority, and state clearly when the data cannot confirm suitability. | Never infer accessibility from a park/parking tag alone. Recommend confirming directly with the site manager; this scenario depends on uneven regional data and needs validation before any coverage promise. |

### Shared behavior when the plan cannot be fully answered

| Situation | Required behavior |
|---|---|
| Place name is ambiguous | Ask for the country/region or offer the likely named-place matches. Do not guess or request coordinates on the OpenAI route. |
| User supplies coordinate-shaped place input | Ask the user to name a destination; do not reverse-geocode or convert the coordinates into a place name. No plan is produced from the coordinate text. |
| User says “near me” but host location is unavailable | Ask for a city/area. Never imply the assistant has GPS access. |
| No suitable public candidate or access evidence is found | Return the best sourced area-level options if available, say what is unknown, and suggest the user verify with the land manager/local authority. |
| Requested date exceeds forecast horizon | Use historical climate only for seasonal comparison; never phrase it as a forecast for that date. Invite a later forecast check. |
| Weather providers disagree | Show each value/source/issue time and explain the disagreement as uncertainty; do not choose a winner without validation. |
| A provider is unavailable or fields are missing | Return a partial plan with explicit unavailable fields and keep valid astronomy/event calculations. Do not fill gaps with unsourced guesses. |
| Requested event/source is not supported | Explain the boundary, link to a suitable authoritative source where known, and avoid fabricating a complete event listing. |

#### Review findings and decisions to close before implementation

| Finding | Review assessment | Groomed decision |
|---|---|---|
| Text-based place discovery depends on more than the assistant's own web search | Native web search differs by host and cannot be a reliable cross-platform backend or structured global POI index. Public OSM services also have use limits and licensing obligations. | The NightSky service owns a replaceable place-data adapter and a terms-reviewed retrieval/indexing plan. Host web search is supplemental. Show place provenance and unknown access status. |
| Weather source count is not a quality measure by itself | Different fields, model grids and issue times can make side-by-side values misleading; no forecast is established as the universal winner in the current scope. | Preserve each source independently and label its issue/valid times. Use consistent display units, but only imply a direct comparison when fields and valid windows actually align. Do not blend or rank models; avoid accuracy claims without forecast verification. |
| Learning content has rights and maintenance needs | Publicly readable lessons are not automatically reusable verbatim. ### Learning across the journey

Learning should be available as an optional “explain this” layer within beginner, event, target-planning and astrophotography flows. Each plan can explain why a window is favorable, what a term such as radiant/culmination/astronomical twilight means, how to find an object, and what the user might learn from observing it. For astrophotography, V1 can teach a guided first-session workflow that adapts to the camera/device and lens details the user provides, while clearly labeling exposure settings as starting points. The assistant should keep explanations tied to the selected location, date and activity, and allow users to ask for more or less detail. After an outing, a user can ask what an observed object was or what to try next; this can work conversationally without saving an observing history in V1.

This is a distinct user need, not a separate learning platform: NASA skywatching guidance explicitly combines beginner concepts, visible objects, app/map handoffs and family-oriented learning, while Sky & Telescope organizes beginner material around learning the sky and using charts. NightSky can connect that learning to an actual plan. References: [NASA Skywatching FAQ](https://science.nasa.gov/skywatching/faq/), [NASA beginner skywatching guide](https://science.nasa.gov/solar-system/skywatching/night-sky-network/may2024-night-sky-notes/), [NASA constellation activity](https://science.nasa.gov/learn/heat/resource/activity-tracing-constellations/), and [Sky & Telescope Stargazing Basics](https://skyandtelescope.org/astronomy-resources/stargazing-basics/).

### Location handling

Location handling is host-specific. Use a named place as the portable baseline across assistants. `resolve_place` accepts either a named destination or `useApproximateHostLocation: true`; the assistant sets that flag only when the user explicitly asks about their current area. A documented host location hint may be used transiently to resolve a named place, then discarded; without the flag, ignore the hint. Do not return the hint's coordinates. No V1 tool asks for raw GPS coordinates or addresses, and typed coordinate text is rejected. If the user supplies coordinates, ask them to name a destination; never convert or reverse-geocode those coordinates into a place name. OpenAI may provide a best-effort location hint in tool-call metadata, which may be absent; do not assume Claude or Gemini provides equivalent metadata. See [OpenAI plugin location guidance](https://developers.openai.com/plugins/plugin-guidelines) and the [tool metadata reference](https://developers.openai.com/plugins/reference).

If a later NightSky website experience offers “near me,” request browser location only after the user chooses that action. Use the selected coordinate only to return that plan, round it to the precision needed by the forecast source, and do not retain a location history. Explain that the planner’s server and data providers may receive the chosen location. V1 has no shareable plan link.

### Data-processing rules

Every external-data adapter must preserve a small source registry with:

- Provider and source URL.
- License/terms, required attribution and whether commercial use is allowed.
- Data class: forecast, observation, historical reanalysis/climatology, calculated value or user-provided context.
- Provider issue/update time and forecast valid time where available; include a retrieval/check time only when the provider supplies no adequate freshness signal and the user needs it.
- Local time zone and units.
- Data coverage, model/resolution where available, and missing values.
- Provider-specific cache expiry and request limits.
- Clear distinction between forecast, estimate, observation and calculated event.
- Source degradation behavior and a contact/terms review date for services that can change terms.

If one provider fails, return the remaining valid parts of the plan and identify what is missing. Never fill a missing value with a model guess presented as sourced data.

Forecasts and climatology must never be blended into one probability or score. The user should be able to see which source and model support each condition. A “good night” comparison can summarize trade-offs, but it should retain the underlying values and state which factors were unavailable.

Gear recommendations can initially be generated by the Prepare for the outing skill using the plan result; they do not require a separate tool. V1 excludes write tools. For read-only public lookups, expected annotations are read-only, non-destructive and open-world when the tool queries external public data.

### Shared output fields

Where relevant, tools should return:

- A stable public place or event reference for follow-up calls.
- Local time zone and unambiguous timestamps.
- Conditions with units and valid-time ranges.
- Source name and user-openable source URL.
- Data class (forecast, observed, historical/climatology, calculated or user-provided).
- Provider issue/update time and valid time; retrieval/check time only when needed because source timestamps do not provide a usable freshness signal.
- Model, spatial resolution or data vintage when the source supplies it.
- Availability state such as available, unavailable, not covered or unknown.
- A confidence/uncertainty note appropriate to the source and lead time.
- Human-readable reasons, without an unexplained aggregate score.

## V1 success criteria

V1 is ready for a real-world pilot when:

1. A user can complete the journey from activity and location to a sourced, time-specific observing plan without manually joining several data sources.
2. The defined event classes work across the supported date ranges and return local times correctly, including high-latitude cases with no astronomical night.
3. Every forecast and modeled value includes its source and freshness or vintage; missing coverage is explicit.
4. A provider outage produces a useful partial result rather than a fabricated complete answer.
5. Public candidate locations are never described as verified, legal or safe unless a current authoritative source establishes that status.
6. The five skills select the intended tools for direct and conversational requests, and the tools also return useful results without a skill or map UI.
7. The core journey stays free to the user, uses no paid data/API, complies with the selected source terms and quotas, and fits an explicit operating-cost ceiling.
8. Forecasts, satellite observations and historical climatology remain visibly separate in tool output and any later map UI.
9. Every data source in production has an approved terms/attribution entry and a fallback or a clear unavailable state.

Pilot measures should include successful completion of a plan, whether the user would act on it, the condition explanations they found useful, and where source coverage failed. For the public launch, also track plugin installs if the platform reports them, activations/first successful plan where observable, repeat use, plan completion, tool-call success/error, latency, provider coverage/outages, and referral-link clicks. MCP tool-call counts do not equal unique users or installs. Confirm which marketplace-level metrics are available at launch; collect only minimal, disclosed, privacy-respecting service telemetry. These measures test usefulness; they do not by themselves establish market size.

V1 is the complete product capability boundary intended for local testing and a public launch. ### Research-based V1 decisions and feasibility check (10 October 2026)

| Question | Finding | Recommendation |
|---|---|---|
| Is the current website already the hosted MCP product? | The repository has a Vite/Express app and Netlify configuration publishing `dist/public` as a static site. ## Market context

Adjacent products already cover meaningful parts of the journey: [PhotoPills](https://www.photopills.com/) plans Sun, Moon, Milky Way and other photography; [Light Pollution Map](https://www.lightpollutionmap.info/) maps sky-brightness layers and measurements; [Clear Sky Chart](https://www.cleardarksky.com/csk/) and [Astrospheric](https://www.astrospheric.com/) focus on observing forecasts; [The Nightmap](https://app.thenightmap.com/) and [Starry Spots](https://starryspots.com/) combine dark-sky locations with community/map features. Their current product pages confirm substantial overlap in maps, place discovery, weather and sky timing. That means “a map,” “community spots,” or “AI planning” alone is not a defensible wedge.

A possible wedge to test is a source-transparent, cross-location trip decision: compare candidate places and nights, explain what is forecast versus historical, and expose the unknowns that other sources leave to the user to reconcile. Product pages establish feature overlap, not market demand or willingness to switch. The DarkScout relationship to this project remains unresolved and is not counted here as an external competitor until clarified.
