## Concrete gaps in current evidence

`server/plugin.ts` does not configure Express `trust proxy`. Behind a proxy, `req.ip` used by admission controls therefore ordinarily identifies the immediate peer; many users may share that IP budget. Forwarded headers alone do not fix this. Review the actual chain and implement/test a narrowly trusted proxy configuration if individual-client admission is required. Never enable blanket trust based on this document. Global/provider limits and process-local counters also need a deliberate single-process pilot or verified multi-process strategy.

The existing website entry has the local `/privacy`, `/terms` and `/support` pages; the standalone service mounts `/health` and `/mcp` and does not serve those pages. The current intended ownership is the same-repository static website for policy/support pages and Hetzner for MCP. The owner must confirm final policy hosting; dedicated static policy pages are also possible without redesigning the website. Supply and verify the selected hostname and direct-route fallback/HTTPS availability; private-branch drafts do not establish public policy URLs. The standalone `/health` currently has no injected component checks and reports **liveness**, so a 200 response does not prove artifacts are loaded, a tool works, or sources are fresh. No target-host logs, TLS, rollback, capacity or official platform connection have been observed locally.

## Local validation procedure before deployment authorization

1. Use the canonical [deployment checks](deployment.md#local-release-checks) to record build/runtime results against the exact revision. Retain image identity separately if a Linux container build is available; a Windows Node run does not establish Linux image behavior.
2. Prepare a private environment file from the table with real owner values. Check each artifact's SHA256 against its independently reviewed manifest, its size against the candidate limit, and file permissions against the non-root container user. Do not generate replacement expected digests merely because validation fails.
3. Rehearse the immutable image locally with reviewed read-only mounts, explicit mode/allowed hosts, and a loopback-only published backend. Record `/health` as liveness. Initialize a real MCP client and list tools: resolver mode must list only `resolve_place`; full mode must match the reviewed package. Use synthetic named destinations and the cases in [resolver scan preparation](../platforms/location-tool-scan.md); never use personal hints in evidence.
4. With the planned local reverse proxy, repeat MCP initialization/tool calls and hostile Host/body cases; confirm backend bypass is unavailable. Specify the exact trusted peer addresses/subnets and hop topology before changing trust behavior; the public edge must overwrite attacker-provided forwarding headers. Validate IPv4/IPv6 client addresses, direct forged headers, differing hop lengths and alternate ingress paths, and confirm independent synthetic clients receive the intended IP budgets. Retest if topology changes. Review both application and proxy/container outputs for bodies, query strings, coordinates and identifiers. Any untested proxy behavior stays a hosted gate.
5. Use the existing capacity and fresh-process rollback procedures linked from deployment; record exact limits, request mix, active artifact hashes and restored result equality. Measure startup/peak RSS and disk with the intended artifacts. Local fixture success cannot approve a 4 GiB host with larger indexes.
6. Attach a redacted record of configured inputs, executed commands, result/exit codes and unresolved gates. This document describes a procedure; none of these steps is claimed to have run by its existence. Hosted staging validation, DNS/TLS, official scan and publication await separate authorization.
