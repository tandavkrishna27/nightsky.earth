# NightSky V1 MCP tool contracts

This document records the implemented twelve-tool local V1 contract, updated 14 October 2026. Shared schemas and executed registration are the source of truth. Enabled data retains its verified provenance and measured coverage; future sources and broader coverage remain subject to Task 0 gates. Local implementation does not establish live assistant compatibility or deployment.

## Shared wire rules

- The structured JSON payload is capped at 4 MiB after UTF-8 encoding, enforced by shared schemas and the executed tool-result guard. The MCP envelope/text content adds overhead and is not included in that structured-payload limit. Oversize results fail explicitly with a request for fewer options or a shorter window; native evidence and source attribution are not silently trimmed.
- Results expose at most 64 source records, 20 caveats, 25 sky events, 10 observing-location candidates, 4 independent weather forecasts, 48 weather samples per source, 8 plan windows, and 5 comparison options.
- Every external value is tied to a `SourceRecord`: source name and URL, attribution, data class, plus provider model/product and issue/valid time or vintage when supplied. Calculated values identify the calculation/source and algorithm provenance.
- Weather records represent one provider/model each. They include valid times, forecast lead, units, and per-field omissions. Do not average distinct models into one forecast. Historical reanalysis is labeled historical and never presented as a forecast.
- Every result has an `Availability` (`available`, `partial`, `stale`, `unavailable`, `not-covered`, `unknown`, `unsupported`, or `out-of-horizon`) and a human-readable reason. Source gaps and uncertainty remain visible.
- All instants are UTC ISO-8601 strings ending in `Z`; all user-facing time windows also carry an IANA time zone. The maximum requested range is 366 days.
- `PlaceRef` contains a versioned opaque `placeId`, display name, IANA time zone, source records and gazetteer vintage. Exact coordinates for a named place stay in the server-private `ResolvedPlace`. Public observing candidates can expose their mapped coordinates and navigation link. Approximate host coordinates are request-only and never returned or persisted.
- Locale and unit preferences guide presentation. Source-provided names and scripts are retained; the API does not promise translation that the source does not provide.
- Inputs reject unknown fields. Location-aware tools downstream of `resolve_place` accept only a versioned `placeId`, never free-text coordinates or a street address.

All twelve tools are registered and have tested annotation booleans. Source gates continue controlling newly enabled datasets, field sets, horizons and publication claims. Current acquisition and coverage evidence is recorded in data-sources.md and the data-wave operations reports.

## Core schemas

The TypeScript/Zod v4 source of truth is under `shared/nightsky/`:

| Contract | Module | Required guarantees |
|---|---|---|
| `PlaceRef`, private `ResolvedPlace` | `places.ts` | Versioned public ID and provenance; exact named-place coordinates only in server-private record. |
| `TimeWindow`, `SourceRecord`, `Availability` | `common.ts` | UTC order/range and IANA validation; traceable provider/calculation provenance; explicit availability reason. |
| `WeatherForecast`, `NightConditionsResult` | `weather.ts` | Forecast-only data class, independent source records, forecast lead, per-time values and missing-field reasons. |
| `AstronomyWindowResult`, `TargetVisibilityResult` | `astronomy.ts` | Local intervals/polar state and supported target geometry. |
| Historical cloud context | `climate.ts` | Reanalysis-only data class; period/method/source, explicit sample/baseline distinction and independently validated completeness. |
| `EventResult` | `events.ts` | Ordered optional event times, explicit local visibility state, source record per event. |
| `PlanResult`, comparison and app recommendations | `planning.ts` | Sources/caveats/gaps retained, explicit factors and actionable preparation. |

## Permissions and privacy

No NightSky accounts, OAuth requirement, user writes or query-history database are part of V1. Bounded in-process caches and short-lived traffic counters are distinct from user query history. Source-maintenance credentials stay outside the repository and runtime. The assistant should set the approximate-location flag only for an explicit “near me/current area” request. The service may send rounded destination coordinates to the selected provider, as described in the product privacy notice. Do not log or persist host location hints or query histories. Executed request/provider budgets and bounded salted-subject/IP counters are covered by transport tests. A subject hint is untrusted traffic context, not identity or authorization. The metadata adapter reads only consented finite location hints, rounds to two decimals and discards unrelated metadata. Application logging retains fixed route/status/duration labels; hosting/proxy retention and replica limits remain deployment gates.

## Operator-only resolver rehearsal

The default registry remains the twelve-tool full mode. The standalone backend accepts `NIGHTSKY_MCP_TOOL_MODE=resolver-only` for a guarded one-tool rehearsal; unknown values fail startup. Programmatic `toolMode` is operator configuration, never a tool argument or request metadata. Resolver-only exposes only `resolve_place`, retains body/Host/rate/metadata/output guards and starts no provider lookup. This prepares Task 4B locally; it is not an official location scan or hosted draft.
