## Actual limits: serving pairs and lineage are different

The initial legacy manifest has a 10,000-pair limit, but **current schema-4 catalogue is not globally limited to 10,000 pairs**. Source inspection of `catalogEra5.ts` establishes up to 256 children, each up to 10,000 pairs: 2,560,000 theoretical pair slots. The named inventory needs at least six children by pair count alone; the conditional full rectangular quarter-degree grid (1,038,240 nodes before timezone multiplicity) needs at least 104. Both counts fit that structural ceiling, without establishing byte-size, memory, throughput, timezone or release admission.

A separate genuine **global 10,000-lineage ceiling exists in the current publication and closure paths**. `scripts/era5/build-catalog.ts` accumulates `mergeReleaseRevisions` across every child; `shared/nightsky/operatorClosure.ts` independently repeats that union. The merge key is `kind|revision`; conflicting hashes for the same key reject, and more than 10,000 distinct keys reject. Per-child metadata has the same bound. The root digest does not waive the global union, and splitting into six or more children does not increase lineage capacity. The earlier metadata conclusion that only per-child lineage was bounded was incorrect and is corrected here.

The actual observation builder names raw and decoded revision keys from their SHA-256 values, so distinct raw parents and decoded partitions count globally; plan/manifest lineage adds entries. Production admission must count **R distinct raw keys + D distinct decoded keys + M distinct manifest keys <= 10,000**, with every local child also within its bound and no conflicting same-key hashes. Reusing an unchanged raw parent deduplicates that raw key; renamed jobs do not erase distinct decoded bytes. The existing one-cell, at-most-monthly planner is incompatible with this bound for the full named baseline: even ignoring retained subtraction, each of 54,822 cells needs at least one distinct single-cell source parent and decoded partition (already over 109,644 keys before manifests), and full thirty-year monthly fragmentation is much larger. Actual retained subtraction covers only seven cells and cannot remove this structural mismatch. A reviewed acquisition/partition/provenance layout must fit the current global union, or the lineage representation must be separately redesigned and validated. Larger multi-cell/time-range parents might reduce raw count, but the existing <=10-cell/800-hour decoded partition contract still requires explicit global accounting. ARCO metadata alone neither solves that bound nor establishes provenance equivalence. No runtime code or lineage ceiling changed in this lane.

Named places do not cover all oceans, poles or arbitrary coordinates. The full global target remains open; record timezones establish no global zone polygons. These are different outstanding inventories, not permission to reduce scope.
