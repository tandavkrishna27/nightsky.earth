## Recommended finite route and arithmetic

Prefer on-demand original selected-region geometry plus local point-in-polygon classification. It avoids both a maintained global catalogue and point-by-region network fanout. The offline component below implements a bounded subset; the network route remains a proposed design.

With R unique selected included/excluded regions and Q positive candidate queries, cold acquisition requires R + Q requests. Assuming already-resolved selected IDs, limit=20 candidate pages, no pagination and no retries, existing maxima give R <= 10 and Q <= 5: at most 15 requests, reserving conservatively 2R + Q = 25 credits when requesting both details features. Local classification of at most 100 points against ten geometries creates at most 1,000 evidence rows with zero further requests. At the current single-flight, one-second-start-spacing policy, fifteen starts alone consume at least fourteen seconds; the fifteen-second total deadline cannot reliably accommodate responses. Cache hits cannot justify a cold-path budget. The existing 262,144-byte response cap can also reject large country geometries; silently simplifying them would change the membership contract.

The remote point-set operation alternative costs up to 2R + Q = 25 requests and conservatively 3R + Q = 35 credits on a cold path **only when each region is one supported Polygon**. MultiPolygon handling for that operation was not established; splitting it introduces further calls. It supplies no practical improvement to the existing five-request envelope. Repeated per-point `part-of`, reverse-geocoding labels, bounding boxes, region centroids and country strings are rejected as substitutes. Boundary IDs and selected place IDs require explicit identity/revision binding.

No production network adapter was added. A fake fetch can legitimately test documented response handling; unknown source vintage and provider edge semantics are not prerequisites to offline implementation. Snapshot-relative local semantics are sufficient for that implementation, provided they remain explicit. Separate activation still requires the selected budget, source-response checks and admission update. Existing pure composition fixtures remain useful and inactive.

## Offline component and limits

`server/places/api/geometrySnapshot.ts` decodes a caller-supplied original-geometry response plus a receipt identifying the selected region/revision, upstream ID, requested details features and fetch/expiry times. It requires one matching `details` Feature with Polygon/MultiPolygon geometry. The receipt is not evidence that a live fetch occurred. The decoder hashes normalized geometry, region revision, receipt and policy into a geometry revision; coordinates remain private in a closure. It exposes unknown source vintage explicitly. Classification is relative to that snapshot, not a certified legal boundary.

The local policy uses linear GeoJSON longitude/latitude segments and a 1e-9-degree distance-to-segment ambiguity band. This is a numerical policy, not source accuracy. Shells and holes are orientation independent; hole interiors are outside and shell/hole edges are unknown. Disjoint MultiPolygons and explicitly split antimeridian parts are supported; unsplit edges spanning 180 degrees or more and polar vertices are rejected. Invalid/self-intersecting/touching rings, nested holes and overlapping/nested component shells are rejected, including some otherwise valid geometries outside this conservative subset. No automatic simplification, repair, wrap or centroid fallback occurs.

The decoder caps response text at 262,144 UTF-8 bytes, total closed-ring positions at 1,024 and total rings at 32. These limits bound quadratic topology validation and will exclude many complex country/state geometries; this component is not launch-ready global coverage. It also conservatively rejects rings whose absolute doubled planar signed area is at most 1e-9 square degrees; the threshold has area units and is separate from the distance ambiguity policy despite sharing its numeric value. Lifetime is at most one hour; future/expired evaluation returns unknown. There is no cache, acquisition, automatic evidence-row integration or discovery registration. Higher geometry limits require profiling and an explicit revised bound.

Response-shape basis: the Place Details feature table calls `details.full_geometry` a details feature modifier, while its extraction example selects `properties.feature_type === 'details'` and describes one details Feature. The decoder follows that documented shape and requires a matching `properties.place_id`; it does not interpret a radius/geometry feature as the administrative boundary. A separately authorized source fixture must verify this combination before activation. The docs' narrative uses comma-separated feature names while its generated reference mentions `|`; no request serializer has been added, and this discrepancy must be resolved before acquiring responses.

`tests/places/api-geometry-snapshot.test.ts` uses synthetic response strings to cover shells/holes/orientation/ties/epsilon, split and unsplit dateline cases, MultiPolygon, invalid topology, byte/ring bounds, wrong identities, changed revisions and expiry. These are local algorithm/decoder assertions, not actual-source acceptance.

## Finite decisions, not another research cycle

1. **Preserve the five-request envelope:** after source acceptance, support only combinations whose complete cold acquisition and candidate queries fit it. For example, one positive query plus up to four unique region geometries fits the request count, but geometry byte limits, credits and timing still need acceptance. Queries above the cap stay explicitly unsupported. This is a reduction from the original full combination requirement and requires an owner decision.
2. **Preserve all five-plus-five region combinations:** approve a separate bounded geometry stage with at most ten acquisitions, twenty reserved credits, explicit byte/vertex caps and a measured deadline, followed by the existing at-most-five candidate searches. Keep failure/oversize/unknown as partial or unavailable. This changes the current envelope; do not activate it implicitly. A maximum geometry size remains a supported-scope limit, not justification for an owned global catalogue.
3. **Keep the present scope:** leave G2 unmet and retain exact-site, circles and existing region unions. Optional host search can identify candidates or official access information, but cannot certify administrative membership or erase exclusions. Host-search absence remains explicit and does not become a provider fallback.

The finite actual-source acceptance packet is: selected country/state identity and parent-child binding; an original Polygon with a hole; MultiPolygon/island; antimeridian region; points inside/outside/on the boundary under the local policy; selected-region change/expiry; oversized response; missing geometry; and unavailable response. Record source timestamp/version if actually supplied, otherwise preserve unknown vintage and the snapshot-hash freshness policy. Provider certification of the local algorithm is not required. No blanket source completeness or all-country geometry-size promise follows.
