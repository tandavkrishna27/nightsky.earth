# Global request inventory and bounded lineage follow-on

Status: offline proposed acquisition inventory; no request execution, serving installation, or scientific completeness claim. The original nine-part completion checklist remains partial. This lane does not complete baseline data acquisition, solar aggregation, or global serving.

The frozen inventory pins all 236,042 named destinations, 54,822 unique ERA5 source cells and 56,039 cell/timezone pairs across 48 named inventory batches. `plan-global-history.ts` validates every batch with the existing strict inventory schema and exact `suppliedCellKey` mapping, then compares the global cells and pair files. Shared cells across batches have one acquisition owner. Destination batches remain mapping evidence; they do not become separate source request schedules.

## Exact compact schedule

The source clock is half open 1990-12-30T00:00Z through 2021-01-03T00:00Z, 263,088 hours and 362 UTC month templates. Each spatial rectangle references all templates; sparse overrides replace only months with retrieved observations. Expansion is executable with `expandGlobalHistoryRequests(plan)`: it yields a single concrete request and full identity SHA-256 at a time. Empty override shapes omit a fully retrieved month. Dates use real calendar month lengths and the two partial boundary months. No 14.4-billion-element hourly array and no solar calculation is used.

Spatial partitioning owns grid **nodes**, not continuous square areas: inclusive row/column bands contain two or three quarter-degree nodes and the next band starts at the previous final node plus one. Thus neighboring request rectangles never share a source point. Retained four-node Hanle and six-node Kodaikanal/Munnar rectangles are forced bands; remaining gaps partition into bands of two or three nodes. A singleton gap, crossing forced intervals, nonrectangular retained grid or incompatible per-cell retained hour masks fails closed. This is explicit admission of this frozen evidence, not a general optimizer for arbitrary retained geometries.

Longitude nodes are -180 through 179.75; +180 has the canonical -180 identity. Latitude nodes include -90 and +90. Partition tests prove every node belongs to exactly one band, including edges. Only bands containing at least one required cell produce requests. Their filler cells are explicit, have no timezone pairing and establish no named coverage. Every rectangle has extent at least 0.25 degrees, at most nine cells, 744 timestamps and 6,696 scalar cell-hours; both hourly and scalar limits remain below the existing 22,320 grouped parent ceiling. Current provider acceptance and transfer bytes are still unproved.

All retained decoded partition, raw parent and ledger pins are reread locally; decoded headers require final revision 1/0001 and member zero. Actual samples, including nulls, establish retrieval. Overlap conflicts stop admission. Subtraction includes every acquired rectangle cell, including fillers; all cells inside a rectangle must have identical retained hour masks. The required named-cell subtraction is 16,416. The all-engineering-cell retained total is separately counted; target remaining source hours are 14,422,993,920. A retrieved null is never treated as fresh request authority.

Unique admitted source inputs are capped at 128 MiB; each attempt enforces a 128 MiB physical read cap. The explicitly authorized two-attempt recovery has a combined 256 MiB physical read cap within the original cooperative ten-minute window. New output remains capped at 256 MiB. Publication creates an immutable output exclusively, removes its own temporary file after failure, and never overwrites. The source is a collection of pinned byte snapshots read through stable-identity checks. Budget/deadline failure stops; there is no automatic restart, cap increase, retained exclusion, or scope reduction.

## Why the existing source union cannot admit the result

`tiledEra5ManifestSchema.sourceRevisions` admits at most 10,000 rows. `mergeReleaseRevisions` deduplicates by **kind + revision**, rejects different hashes for that same key, then rejects the union above 10,000. `publishClimateRelease` invokes this across all supplied tile shards, and `publishClimateCatalog` invokes it again across every release child. Splitting the 56,039 pairs into catalog children therefore solves routing size but does not solve the catalog publisher's global lineage union. The catalog's `sourceRevisionsSha256` field is a hash of that flat global array; it is not a traversable bounded lineage representation.

Each concrete proposed monthly request has a unique tile/template/shape identity. Under the existing job revision convention it requires one raw revision row and one decoded revision row (each request has <=744 rows, so it fits the 800-row decoded partition limit). Every retained raw, decoded and metadata row must also remain represented. Raw and decoded checksums themselves are not knowable until acquisition; request pins are not substitutes for source pins. The schedule count report quantifies these prospective revision rows, not acquired files.

## Concrete next schema and three integration points

This section records the reviewed architecture contract. The schema-5/schema-6 implementation and its explicit offline publication/operator interfaces are documented in `bounded-era5-lineage.md`; the completed full-scale synthetic acceptance is recorded in [the lineage evidence](data-pilot-evidence/2026-10-16-bounded-lineage-scale.json), with its measured resource bounds and limitations. No existing flat source cap has been raised.

1. **Publisher and strict schemas:** Add a schema-5 catalog with the schema-4 coverage directory plus `lineage: {format: 'era5-lineage-radix-v1', rootPath, rootSha256, rootBytes, uniqueRevisionCount, rawCount, decodedCount, manifestCount, membershipRoot}`. Its children are new **schema-6 release roots**, not schema-3 roots. Schema 6 preserves bounded coverage shard routing but removes the flattened top-level `metadata.sourceRevisions` and the repeated `shards[].sourceRevisions` arrays. Each release root instead has a bounded `sourceLineage` root descriptor and each shard descriptor contains a digest of that shard's bounded canonical source array, in addition to the existing manifest path/hash/bytes and coverage keys. Schema-2 tile manifests retain their original at-most-10,000 source rows, so a provider can still read and check an individual shard with the established contract. Schema-3/schema-4 remain supported for small releases; their caps are unchanged.

   The catalog and each schema-6 release use strict lineage leaves with at most 2,000 sorted `{kind, revision, sha256}` rows and at most 512 KiB. A strict radix node contains at most 16 child descriptors `{nibble,path,sha256,bytes,count,firstKey,lastKey}` and is at most 16 KiB. Route on the first four SHA-256 hex digits of `kind + '|' + revision`; four levels permit at most 65,536 leaves and 131,072,000 rows **per root**, independent of the 256 coverage children. A full bucket stops publication; no automatic rehash or cap increase. The canonical root hash commits every raw/decoded/metadata row. Root count totals and per-kind totals must equal the admitted union. A domain/version string is part of every canonical node hash.

   A second bounded membership hierarchy has the same radix/fanout/leaf byte bounds. It records publisher-verified edges: catalog-to-release lineage root digest, release-to-shard manifest digest, and shard-to-canonical-source-array digest, including source-row count and per-kind totals. The publisher verifies the complete source-row subset for each edge before committing it; a membership record is never accepted merely because a child claimed it. This permits runtime verification of an already verified bounded shard array by its digest, while retaining **all individual raw/decoded pins** in the lineage hierarchy. A grouped digest alone never replaces those pins. Canonical membership keys include edge type and parent/child identities; duplicate keys with conflicting digests fail.

   The publisher streams all pinned shard source arrays through bounded external sorting by `(bucket,key)`, with declared memory and explicit temporary/output byte budgets, constructing release roots and then the global union and membership roots. Same key/different hash fails even across different coverage children; same key/same hash deduplicates. Publication orders leaves, nodes, schema-6 releases, then catalog root exclusively. Inputs are revalidated before final root publication. A crash may leave unreferenced immutable objects but never an admitted partial catalog.

   This explicitly removes the insufficient `256 children  times  10,000 source rows = 2,560,000` ceiling. A coverage child may reference millions of lineage rows through its bounded tree; it does not embed that union. At most 1,000 shard descriptors per release and ten coverage keys per shard retain 10,000 pairs per child, while the global 256-child directory still admits 2,560,000 pairs. Source-row capacity is separately bounded by the lineage tree, so the actual 56,039 pairs and prospective 18,033,376 raw/decoded revision objects are both within distinct declared capacities.

2. **Provider admission and cache:** `catalogEra5.ts` dispatches schema 5 explicitly while retaining schema 4; `releaseEra5.ts` adds explicit schema-6 dispatch while retaining schema 3. The catalog verifies its pinned global lineage and membership roots and a catalog-to-release membership edge before admitting a coverage child. On shard load, the release provider reads the pinned schema-2 manifest, validates its existing at-most-10,000 source array, computes its canonical digest and checks the release-to-shard and shard-to-array membership edges. The previously publisher-verified membership root commits the subset proof; runtime does not rescan a million-row child union or issue one global-tree read per source row. Missing edges, wrong parent/child identity, altered digest/counts, unknown format or malformed nodes return unavailable. Coverage keys alone never establish lineage membership.

   The complete raw/decoded/metadata records remain inspectable through the pinned lineage tree for offline audit and explicit provenance inspection. Membership trees accelerate runtime admission; they do not discard records or resolve conflicts. Lineage and membership node/leaf buffers share the existing **32 MiB total cache** with release/tile data; an explicit 2 MiB reservation reduces aggregate cache allocation to 30 MiB. Entries are keyed by path and expected digest. Each traversal is depth four with bounded file reads; one lookup verifies only a bounded number of membership edges for its selected child/shard, and never recursively scans a whole tree.

3. **Operator admission and evidence:** The offline catalog operator explicitly selects schema 5, supplies the pinned coverage-child inventory and lineage build budgets, and receives the pinned catalog and lineage root only after a successful global merge. Its public evidence records exact coverage pair count, original named inventory pin, unique revision/per-kind counts, root digest, maximum leaf size, disk/memory budgets, conflict checks and provider fixture results. Existing schema-4 publication remains available for small releases; it cannot silently fall back from a failed schema-5 build. Recovery requires explicit reuse or abandonment of the failed work directory and a new operator decision.

Required migration fixtures: cross-child same-revision conflict; identical overlap; altered root/interior/leaf pin; wrong radix prefix; missing membership; unknown/extra fields; duplicate or reordered keys; count tampering; 2,001-row bucket; child-boundary routing; 32 MiB cache accounting; unknown schema fallback; unchanged schema-3/schema-4 results. Acceptance must include both a 10,001-key small fixture and a full schedule-derived synthetic union of **at least 18,033,376 distinct raw/decoded revision keys plus retained/new metadata**. The latter must use the actual 56,039-pair child/shard routing, include a coverage child with more than 10,000 unique source rows, verify every source pin survives the global and child trees, and reject a same-key/different-hash conflict across separate coverage children. It must publish under declared memory/disk/deadline budgets, show every bucket fits 2,000 rows/512 KiB, and serve a selected shard through pinned membership edges within the 32 MiB total cache without creating any flat global/child >10,000 runtime array. A test that only lifts the root union or keeps schema-3 child unions is insufficient. These requirements were subsequently exercised by the bounded-lineage implementation and its single supervised full proof: 18,033,393 synthetic pins, all 56,039 pair routes and six children. See [the owning implementation and evidence](bounded-era5-lineage.md#evidence-and-limitations). Request-derived keys were assigned sequentially to the actual pair routes, without real acquisition-rectangle attribution; full operator closure was not separately measured at this scale. This synthetic engineering acceptance does not establish source acquisition or scientific coverage.
