# Offline source admission preparation

The [machine-readable inventory](source-admission-inventory.json) contains **429 individually inventoried gbOpen ADM0/ADM1 layers, 18 original licence labels and all eight proposed dated Geofabrik extracts**. Every source remains quarantined. This is an actionable preparation packet and validator; it does not authorize acquisition, clear rights, enforce the existing geography publisher, or promote runtime data. Original completion counts are unchanged.

The packet uses retained evidence only: **zero new requests, zero response bytes**. There is no new public request ledger to reconcile; the JSON records an empty ledger and pins the previous sanitized ledgers. No geometry, dataset, account, credential, model, installation, deployment or deletion operation occurred. No CDS asset host is enabled because retained official documentation does not establish an exact host. The existing history executor must retain its own fail-closed host policy.

## CLI and data contracts

The standalone [module](../../scripts/osm/source-admission.ts) exports `buildRetainedSourceAdmissionInventory`, `buildRetainedSourceAdmissionPolicy`, `admissionSubjectDigest`, `validateSourceAdmission`, `validateSourceAdmissionFiles`, `sourceAdmissionOutputPath`, and strict schemas for bundles, manifests, trust, operator policy and evidence pins. Its boundary policy is scoped to these geoBoundaries inputs; its OSM policy is scoped to the proposed Geofabrik route.

Generate a new report inside this worktree, in an existing directory:

```text
node --import tsx scripts/osm/source-admission.ts inventory NEW_OUTPUT.json
node --import tsx scripts/osm/source-admission.ts validate BUNDLE.json TRUST.json NEW_RESULT.json
```

`inventory` verifies both immutable input pins before generating the full packet. It refuses overwritten output, output outside the workspace, traversal and symlink paths. Both CLI commands inspect every original output path component before normalization or opening a file: NTFS stream colons, reserved Windows devices, trailing dots/spaces, control characters, empty/dot components and device/UNC namespace syntax are rejected on every platform. Only a native absolute drive root may contain a colon. No network code or automatic fallback exists. Its input ceiling is 8 MiB total with individual retained evidence <=4 MiB; output is <=8 MiB.

`validate` reads a strict schema-version-1 bundle and a **separate operator-controlled trust file**. It independently rebuilds the baseline source policy from the two hardcoded canonical retained evidence pins at the module's repository root. Neither the candidate nor its trust file can select or replace that baseline. Bundle/trust JSON each have a 2 MiB ceiling. Every referenced metadata/review file is <=4 MiB and verified by byte count and SHA-256, under a combined 16 MiB input ceiling including descriptors and physical retained policy-root bytes. Repeated identical pins at the same absolute path count once; different roots do not share verification. Evidence paths are bounded safe relative paths resolved from their owning descriptor, without traversal, Windows special path segments or symlinks. Dataset and geometry bodies are not read. Output must be a new workspace file. Quarantine produces a report and exit status 2; invalid input/pins fail without a result. An unresolved source is never silently skipped.

The bundle's `source` binds key, kind, immutable edition, manifest pin, inventory `recordSha256`, exact original asset identity/URL/provenance pin, exact payload URL/bytes/SHA-256/identity evidence, intended transformations/distribution/output licence, and rights/licensor/terms/notices/condition evidence. An OSM source additionally requires exact clip URL/bytes/hash, evidence binding it to that payload hash and the extraction procedure. A public ODbL derivative requires its concrete offer URL, exact output bytes/hash and availability policy. Notice destinations, modifications, provider attribution and mixed-output compatibility need reviewed evidence.

The referenced manifest is a separate frozen **metadata** document with this shape, enumerating the exact sources proposed for later acquisition review:

```text
{ schemaVersion: 1, kind: "source-admission-manifest", records: [
  { sourceKey, kind, edition, recordSha256, payload: { url, bytes, sha256 } }
] }
```

Duplicate keys, a missing source or disagreement with the bundle's exact edition/record/payload fails. The retained inventory cannot be used as a completed acquisition manifest while payload identity is unresolved. Copying an unknown field or an LFS claim into a measured-payload field is unsupported. Source and payload review receipts must establish those facts before a new manifest is accepted.

The candidate's acquisition manifest does not define its original licence policy. `validateSourceAdmission(bundle, trust, trustedPolicy)` requires an independent operator-trusted policy context; omitting it fails. `buildRetainedSourceAdmissionPolicy()` derives 437 exact policy entries from the pinned original inventory: key, kind, edition, inventory record SHA-256, original licence profile, mandatory conditions and reviewable/blocked disposition. Boundary record hashes are the inventory's `recordSha256`; OSM record hashes are canonical digests of their exact retained OSM records and are exposed by this policy builder. The pure validator matches the full source tuple against that context and enforces the original profile and all policy conditions, even when a candidate declares a different supported licence and supplies fresh otherwise trusted receipts. Every result retains the policy ID, canonical policy digest and pinned inventory roots.

POL ADM0, TWN ADM0 and the conflicting IND ADM0 record are blocked by the retained policy. Generic source/rights/admission role approvals cannot remove these holds. Changing an original licence, resolving a provider identity conflict or replacing a source requires an explicitly reviewed replacement inventory/policy revision. The CLI currently supports only its retained baseline; enabling a replacement requires an explicit code-reviewed policy-root/pin change. A pure API caller must obtain replacement policy context through its own independent operator approval process. Passing candidate-generated policy context would defeat this trust boundary and is not supported.

Required approval roles are `source-provenance`, `payload-validation`, `rights-review`, and `admission-approval`, plus `effective-clip` for OSM. Each receipt binds the canonical SHA-256 of the **entire source object**, reviewer, review time and explicit approve decision; its evidence pin points to a strict receipt document `{schemaVersion:1, role, subjectSha256, reviewer, reviewedAt, decision:"approve"}`. The file gate verifies both its bytes and agreement with the receipt. Rights/source/payload/clip evidence remain independent pinned metadata records bound by that subject.

Trust is `{schemaVersion:1, trustedReviews:[{role,subjectSha256,reviewer,evidence}]}`. The caller/operator must control this allowlist and the original-source policy context independently; neither may be generated automatically from a candidate's declarations. This is explicit review trust, **not cryptographic reviewer authentication or proof that a grant is legally valid**. The in-memory validator checks the strict objects, policy source bindings and trust identities; callers needing file integrity must use the file gate. A caller controlling policy, trust and candidate can assert approvals, so those inputs must not be treated as untrusted self-service authorization.

Changing any source edition, exact payload, original provenance, clip, intended use, notice, rights evidence or condition changes the subject and invalidates prior reviews. Required licence/profile conditions cannot be waived by approval text. Missing, stale, duplicated or untrusted role receipts quarantine the source. There are no automatic promotions from licence labels, source URLs, Git blob identities or an `approved` metadata flag.

Success is named **`prepared-for-separate-acquisition-review`**, with the scope included in every result. It does not authorize data transfer, publication, release installation or changes to the current publisher. An operator must retain the validated result with the later exact acquisition/resource approval, and separately enforce that approval at execution. Future integration must explicitly wire this gate before claiming publisher enforcement.

## Local verification

Fourteen focused tests cover the complete inventory, pointer-versus-measurement distinction, trusted receipts, exact-subject invalidation, OSM clip association, mandatory original/provider licence conditions, strict URLs/paths/bounds, actual metadata/receipt file pins and manifest membership, CLI new-only/workspace output, Windows output aliases rejected without filesystem operations, equivalent LF/CRLF retained evidence, licence downgrade, renamed/hash-substituted sources and blocked original grant overrides. Prepared test cases use an explicitly fictional operator policy and provide no source grant. The file gate quarantines those fictional sources because its independently derived retained policy does not contain them. Isolated TypeScript checking passes. The parent integration lane owns aggregate registration and the final complete test/build/review evidence.

The initial clean-checkout CI run exposed three test scratch-directory failures because `.cache` was absent. All three now use a shared helper that creates the scratch parent recursively before making a unique fixture directory. The CLI regression exercises an initially absent unique parent without removing the shared cache. All fourteen focused tests and isolated TypeScript checking pass after this test-only correction; production logic and retained evidence are unchanged.

The retained JSON's canonical LF representation is **3,012,319 bytes**, SHA-256 `d1fe85b8065285199648661eb78cd93fd5ec48e4bf2c327c0fe015a31d73a22e`. Rebuilding from the pinned inputs is deterministic; no wall-clock timestamp or new metadata is inserted.
