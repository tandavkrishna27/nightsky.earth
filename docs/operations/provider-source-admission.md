# Provider-aware boundary admission — 17 October 2026

`scripts/osm/source-admission.ts` now chooses boundary conditions from the operator-controlled policy record. Candidate bundle fields cannot choose a provider: the strict source schema rejects a candidate `boundaryProvider` field, and provider names in descriptive text have no authority.

Omitted policy classification retains the legacy GeoBoundaries rules. Explicit `boundaryProvider: geoboundaries` applies the same rules. Existing original-licence profiles and source-specific conditions continue to apply. The reviewed v2 policy preserves the earlier 429 boundary and eight extract records and appends two actual Natural Earth records; its overall policy digest changes.

An operator policy record with `boundaryProvider: natural-earth` must have `kind: boundary`, `originalLicenceId: public-domain` and a `naturalEarthIdentity` object containing:

- `originalSourceUrl`: exact source/edition URL, in addition to the exact edition and record digest already required by the policy record.
- `payload`: exact original payload URL, byte count, SHA-256 and identity-evidence pin.
- `licenceEvidence`: exact retained licence-evidence pin.
- `normalizationEvidence`: exact retained normalization-lineage pin.

The policy schema rejects missing identity pins, applying a boundary provider to an OSM source, a Natural Earth identity under another classification, or misleading GeoBoundaries condition IDs in a Natural Earth policy record. The gate compares every trusted Natural Earth identity field to the candidate. Changing any binding fails even when new review declarations are supplied.

Natural Earth requires the common original-source/licensor/payload-chain/mixed-output conditions, the existing public-domain licence profile, and `natural-earth-exact-edition-and-source`, `natural-earth-normalization-and-limitations` and `normalized-boundary-lineage`. The last condition's evidence pin must equal the operator's trusted `normalizationEvidence`. Each condition still needs retained evidence and the full source still needs independently allowlisted provenance, payload-validation, rights-review and admission-approval receipts bound to `admissionSubjectDigest`. The [actual reviewed authority](natural-earth-admission/reviewed-authority.md) covers two exact private retained boundary subjects after genuine independent evidence review and a separate delegated admission assessment. It makes no legal determination or execution allowance.

## Normalized output lineage

The `normalized-boundary-lineage` condition pins a strict UTF-8 JSON document with `schemaVersion: 1`, `kind: boundary-normalization-lineage`, `source: {url, bytes, sha256}`, `transformRevision` and `outputs: [{path, bytes, sha256}]`. The original source identity must equal `source.payload`; the transform revision must equal `source.intendedUse.transformRevision`. Output paths must be absolute and unique after native resolution (case-insensitive on Windows), with at most 1,000 outputs and at most 128 MiB per output pin. Extra fields, relative/traversing paths, missing outputs and duplicate paths fail validation. The lineage document is subject-bound through its condition-evidence hash; declaring a new relation after source review changes that reviewed subject.

The bounded metadata validator verifies the pinned document bytes and its structure/identity linkage. It does not hash original or normalized geometry bodies. The production execution gate must verify each actual normalized shard against these pins and the exact assembly plan, including split-shard/multiple-source mappings. Successful metadata validation alone does not prove the underlying geometry transformation or body truth; independent payload review and actual execution body checks remain necessary. Assembly's existing aggregate boundary/work limits and individual 128 MiB evidence limits remain unchanged.

## Internal validation APIs and trust boundary

`validateSourceAdmissionMetadataFiles(bundlePath, {policy, trust, trustDirectory, policyDirectory?})` is an internal interface for operator-owned code and synthetic tests. It verifies bounded metadata, source manifest membership, policy inventory-root pins (relative to `policyDirectory`, defaulting to `trustDirectory`), source/evidence/review pins, planet linked evidence where applicable, and any declared normalization lineage. Candidate evidence resolves beside the source bundle; trusted reviewer evidence resolves beside `trustDirectory`. Its returned `source`, `bundle`, admission result and `evidenceSnapshot` support execution binding. Snapshots include every read file's absolute path, physical byte count and SHA-256; a path changing identity between reads fails. The execution gate must recheck those snapshots around the bounded producer/assembly phases.

This interface must never receive policy or trust deserialized from an execution candidate. Its context is an in-memory operator authority, not an extra candidate-selected policy file. It has a 16 MiB per-call metadata-read budget, a 2 MiB bundle limit and 4 MiB per evidence artifact. It performs no payload acquisition or body reads.

An optional third argument, `AdmissionMetadataAccounting`, shares `{bytes, ceiling, paths: Map<absolutePath, bytes>}` across multiple internally controlled validations and the execution gate's own metadata reads. The production helper accepts the same resource-only object as its optional second argument. The allowance must have a positive integral ceiling no greater than 32 MiB and a consistent existing path total. Each unseen path's measured size is reserved before body allocation/read, and a previously counted path changing size is rejected. Repeated reads of an unchanged path consume the existing distinct-path allocation; each helper still retains its own 16 MiB read ceiling. This cap can only tighten resource use and cannot supply trust or policy authority. The execution gate passes one 32 MiB accounting object across all bundle validation and its own metadata reads, so a rejected invocation cannot read extra helper evidence before discovering the aggregate bound.

`validateProductionSourceAdmissionFiles(bundlePath, accounting?)` accepts no trust or policy override. Fixed code pins `natural-earth-admission/reviewed-authority.json`, which supplies only the two reviewed private Natural Earth records and eight genuine subject-bound receipts. The same file pins the independent role report, measured observations and separate root admission assessment; each is read, hashed and included in the metadata snapshot. The existing two inventory roots use their canonical LF Git representation; the new authority and every generic review/evidence pin use exact physical bytes. The full policy contains 439 records. No planet record or review is present. Unsigned source bundles still quarantine, and candidate or synthetic approvals cannot enter this fixed allowlist.

`validateSourceAdmissionFiles(bundlePath, trustPath)` and the existing `source-admission.ts validate BUNDLE TRUST OUTPUT` CLI remain compatible offline inspection tools. A caller-supplied inspection allowlist is not production authority. Production callers must use the fixed-context helper and independently enforce its result on the exact source/assembly invocation. Nothing in these helpers authorizes a receipt, build, release or publication.

Validation covers trusted provider selection, unchanged legacy requirements, changed identities with fresh review declarations, strict lineage linkage/output bounds, metadata snapshots and refusal of candidate-selected trust. Separate actual-authority tests verify the adopted source identities and the reviewed private subjects through the fixed metadata gate; the successful native Windows lineage check is Windows-only. Synthetic fixtures convey no real-source grant. None of these metadata checks opens the actual geometry bodies or authorizes a build.
