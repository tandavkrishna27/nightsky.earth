## Actionable local findings

### P2 — reconcile default diagnostic logging with the privacy evidence

`server/plugin.ts:59` installs a JSON diagnostic sink by default, alongside the ordinary request logger at line 56. `server/mcp/requestDiagnostics.ts:12-15,29-43` emits a locally generated per-request UUID, allowlisted protocol method/tool labels, ingress/completion kind, status, elapsed time and bounded outcome reason. Unknown names are replaced with `unknown`/`OTHER`. The UUID is a new correlation value for one request, **not** an assistant subject, session or user identifier. No tool argument, coordinate, query or raw subject is intentionally included in this event schema.

`docs/operations/privacy-and-telemetry.md:13` nevertheless says application logs contain only route/method/status/timing and do not serialize identifiers. `docs/operations/mcp-data-flow-and-logging.md:20` more strongly says MCP logs should contain at most route/status/timing. `shared/nightsky/policies.ts:14` omits the additional diagnostic fields. This is an inaccurate disclosure/evidence boundary, not an established leak of personal planning data.

Suggested exact replacement for the privacy checklist bullet:

> Application request logging uses fixed route labels, HTTP method, status and elapsed time. MCP diagnostics additionally record a locally generated per-request correlation ID, allowlisted protocol method/tool labels, ingress/completion kind and a bounded outcome reason. The correlation ID is not a user or session identifier. These logs do not intentionally serialize request/response bodies, tool arguments, coordinates, raw paths, queries, headers, host hints or raw subjects. Provider errors returned through MCP are sanitized. Hosting and proxy retention remain release checks.

Apply the same factual field inventory to the logging policy and user-facing draft before policy freeze; retain the difference between generated request correlation and user identifiers. Root owns any correction outside this document.
